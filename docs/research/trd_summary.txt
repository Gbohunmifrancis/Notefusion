NoteFusion Technical Requirements Document (TRD) Audio-to-Notation Transcription Engine, Architecture, and Stack Version 1.0  •  July 2026 Prepared for: RealDiamond Digitals, Akure, Ondo State, Nigeria 1. Technical Approach: Why This Is an ML Problem A recurring question during ideation was whether NoteFusion should work 'the way Shazam/Spotify works' or 'the ML way'. These are fundamentally different problems, and only one of them can power NoteFusion: Audio Fingerprinting (Shazam) Automatic Music Transcription (NoteFusion) What it does Identifies WHICH known recording is playing Determines WHAT notes are being played How it works Hashes spectrogram peak constellations; matches against a database of pre-indexed recordings A neural network analyses the audio spectrogram and predicts pitch, onset time, and duration for every note Works on live playing / original music? No — only catalogued recordings Yes — any audio, including improvisation and humming Output Song title + artist Note events → MIDI → MusicXML → staff + solfa Conclusion: NoteFusion is an Automatic Music Transcription (AMT) product, which is inherently a machine-learning problem. Critically, no model training is required for the MVP — mature, permissively licensed, pre-trained open-source models exist. The engineering work is integration, post-processing, and notation rendering, not ML research. 2. System Architecture 2.1 Architecture Decision: Hybrid, Server-First Two viable inference locations exist: on the server or on the device. The recommended approach is server-side inference for the MVP, with on-device inference added in v1.x as an offline mode. Criterion Server-side (MVP) On-device (v1.x offline mode) Accuracy Full-size model, no compromise Quantised model; slightly lower accuracy Device support Works on 2 GB RAM budget phones Needs decent CPU; slow on low-end devices Iteration speed Improve models/post-processing without app updates Model bundled or downloaded; updates slower Connectivity Requires network (mitigated by ~1 MB compressed uploads) Fully offline — valuable in the target market Cost VPS compute (CPU inference is sufficient) Zero marginal cost Privacy Audio transits server (delete-after-processing policy) Audio never leaves the device 2.2 Component Overview The system consists of three components: Android client (.NET MAUI, C#): audio capture, compression, upload, notation rendering, editing, playback, library, export. Transcription API (Python, FastAPI, Docker): receives audio, runs the AMT model, post-processes note events, detects key/tempo, generates MusicXML and solfa mapping, returns a structured result. Notation/render layer: Verovio converts MusicXML to SVG for the staff view (rendered client-side in a WebView or server-side); the solfa view is rendered natively from the structured note data. 2.3 Processing Pipeline Mic → PCM 22.05 kHz mono → encode (FLAC/OGG) → upload → [Server] decode → Basic Pitch AMT model → raw note events (pitch, onset, offset, confidence) → post-process: confidence filter → tempo estimate → rhythm quantisation → key detection → music21: note events → score object → MusicXML + movable-do solfa mapping → JSON response { musicxml, solfa[], key, tempo, timeSig, midi, confidence } → [Client] Verovio renders MusicXML → staff SVG; native renderer draws solfa; playback from MIDI 3. The Tonic Solfa Engine (Core IP) This is the component no competitor has, and it must be engineered with care. Solfa in the target market is movable-do: 'doh' is the tonic of the current key, so correct solfa depends entirely on correct key detection. 4.1 Key Detection Primary: music21 Krumhansl–Schmuckler key profile analysis over the full clip; report confidence. Cross-check: Essentia key extractor; if the two disagree, surface reduced confidence in the UI. Relative major/minor ambiguity is the most common failure; the UI must make switching (e.g., C major ↔ A minor) a single tap, and la-based minor solfa should be applied automatically for minor keys. Manual override always wins and instantly re-maps all syllables (a pure re-labelling — no re-transcription needed). 4.2 Degree-to-Syllable Mapping (Movable Do) Scale degree 1 ♠2/♯1 2 ♠3/♯2 3 4 ♯4/♠5 5 ♠6/♯5 6 ♠7/♯6 7 Syllable (asc.) d de r re m f fe s se l le t Syllable (desc. chromatics) d ra r ma m f sa* s la* l ta t *Regional conventions vary for descending chromatics; make the chromatic syllable set configurable in settings. Octave register is marked with superscript ticks (d’ above, d₁ below), following common Nigerian choral practice. 4.3 Rhythm in Solfa v1: bar-aligned solfa grid — syllables placed under beat positions with barlines, driven by the same quantisation as the staff view. Readable and familiar without full Curwen machinery. v1.x (premium 'formal solfa' export): full Curwen notation — colons for beats, dots for half-beats, dashes for held notes. 5. Post-Processing: Where Accuracy Is Won Raw model output is never publishable notation. The post-processing chain is as important as the model itself: Confidence filtering — drop note events below a tuned probability threshold; suppress sub-50 ms 'ghost' notes. Tempo and beat estimation (librosa) — establish a beat grid; allow user tap-tempo override before recording. Rhythm quantisation — snap onsets/durations to the nearest grid value (configurable resolution: 1/8 or 1/16 default; triplet detection in v1.x). Over-quantisation destroys feel, under-quantisation produces unreadable scores — expose a 'simplicity' slider in advanced settings. Octave-error correction — AMT models occasionally jump octaves; apply melodic-continuity smoothing for melody mode. Voice reduction — for polyphonic piano output, cap simultaneous voices for readability and offer 'melody only' extraction (highest confident line). Key detection → spelling — spell accidentals according to the detected key (F♯ in G major, not G♭) via music21. 6. API Design (MVP) POST /v1/transcribe   multipart: audio (flac/ogg/wav/mp3, ≤ 3 min), options { mode: melody|poly, key?: string, tempo?: int }   → 202 { jobId } GET  /v1/jobs/{jobId} → { status, progress } | { status: done, result } result: { key, keyConfidence, tempo, timeSignature, musicxml, midiBase64,           notes: [{ pitchMidi, startBeat, durBeats, degree, solfa, octaveMark, conf }],           solfaLines: [...], overallConfidence } Returning both structured notes and MusicXML lets the client render solfa natively while delegating staff engraving to Verovio, and makes tap-to-edit trivial (edit the note list, re-derive both views). 7. Accuracy Targets and Evaluation Metric: note-level F1 (a note counts as correct if pitch matches and onset is within ±50 ms), the standard AMT evaluation, computed with the mir_eval library (MIT licence). Reference material: public AMT datasets (e.g., MAESTRO for piano, vocal melody datasets) plus a self-built 'NoteFusion validation set' of ~50 clips recorded on real phones in real target environments — keyboard in a live room, sung melody, choir rehearsal. The self-built set is the one that matters commercially. Targets: ≥ 90% F1 clean monophonic; ≥ 75% F1 clean piano polyphony; graceful low-confidence messaging below usable thresholds rather than silent garbage. Every in-app user correction is a labelled data point: log (with consent) anonymised before/after note edits to build a fine-tuning dataset for a future NoteFusion-tuned model — a long-term accuracy moat. 8. Security and Privacy Audio uploads over HTTPS only; files deleted immediately after job completion (configurable retention: 0 by default). No account required for MVP — library is local (SQLite via EF Core or sqlite-net); nothing personal transits the server. Play Store Data Safety: declare microphone use and transient audio processing accurately (same diligence as prior Play Store submissions). Rate limiting and max-duration enforcement at Nginx and API level to protect the VPS. 10. Development Milestones Phase Duration Deliverable 0. Summary of Recommendations Go the ML route — fingerprinting cannot transcribe; it can only identify. Use pre-trained open-source AMT models; no training needed for MVP. Primary model: Spotify Basic Pitch (Apache-2.0) — accurate, CPU-friendly, instrument-agnostic, mobile-convertible. Keep C# where it is strongest: the MAUI Android client. Put the ML/notation pipeline in a small Python FastAPI service on the existing Dockerised VPS — that is where all the best libraries live. Server-side inference first for accuracy and iteration speed; ONNX Runtime on-device offline mode in v1.x. Treat the solfa engine (key detection + movable-do mapping + octave marks) as the product's core IP — it is the moat. Validate the core magic in a 1–2 week spike on real phone recordings before writing any app code.
