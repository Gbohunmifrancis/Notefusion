# Blog and hymn pages

notefusion.studio has a blog at **/blog** and public-domain hymns in Tonic Solfa at **/hymns**.
Both are plain static pages on Vercel, generated by `tools/blog/build.mjs`.

- **Blog posts live in the API's database** and are written, drafted (with Gemini), checked and
  published in the admin console's **Blog** section. There are no post files in the repository: the
  database is the one source. Publishing asks GitHub to run the website's deploy, which renders the
  live posts into static HTML at deploy time.
- **Hymns** stay files in `content/hymns`, and their pages are generated and committed as before.

```
content/
  authors/francis.md        the author page (/blog/author/francis) and the byline
  hymns/<slug>.json         a hymn's words, credits and public-domain facts → /hymns/<slug>
  hymns/tunes/<tune>.json   a tune's melody (one tune can carry several hymns); with "draft", a tune page → /hymns/tunes/<tune>
tools/blog/
  build.mjs                 content/ (+ --api: the live posts) → web-site/blog, web-site/hymns, sitemap.xml, the home-page strip
  check.mjs                 CI: fails if the committed pages are stale, a link is broken, JSON-LD is invalid…
  indexnow.mjs              pings IndexNow after a deploy
  lib/api-posts.mjs         reads GET /api/blog/published at deploy time
  lib/catalogue.mjs         writes /blog/catalogue.json (hymns, pages, authors) for the API's checks
  lib/render-pdf.mjs        each hymn's and tune's printable solfa PDF (fonts and mark in pdf-assets/)
  lib/collections.mjs       seasons and occasions, writers and composers, first lines (render-collections.mjs: their pages)
  import/                   the Open Hymnal Project importer (abc.mjs reads ABC, ohp.mjs converts, run.mjs writes)
                            and the CCEH tune importer (cceh-crawl.py, midi.mjs, nwc.mjs, cceh*.mjs)
web-site/assets/blog.css    styles for the generated pages (light and dark)
web-site/assets/blog.js     read counts from the API and "Copy link" on blog pages
web-site/assets/hymn.js     staff (OSMD) and piano on hymn pages; the solfa itself needs no JavaScript
web-site/assets/hymns-index.js  the filter box on /hymns (the list itself needs no JavaScript)
src/NoteFusion.*/Blog       the API: posts, topics, Gemini drafting, publishing, site rebuilds
web-admin/src/app/(console)/blog   the console: posts, editor, topics, "Generate with Gemini"
```

## How a post goes from "Generate" to live

1. **Draft.** In the console, *Blog → Generate with Gemini*: the next 1–10 topics in the queue, one
   chosen topic, or a topic in your own words. (Also automatic: every Monday and Thursday at 05:30 UTC,
   06:30 in Lagos, the API drafts the next topic in the queue.) The API's draft worker asks Gemini for
   each post, runs the checks, sends the problems back for **one** revision, and saves the result as a
   **Draft** with its token use. The panel shows each draft arrive.
2. **Edit.** Open the draft: title, standfirst, description (with character counters and a Google
   preview), address, tags, cover, SEO overrides, questions and answers, and the Markdown body beside a
   live preview. The **Checks** panel re-runs as you type: *blockers* (what would break the site's
   build — they stop publishing) and *advice* (the drafter's quality checks). A generated draft that
   still failed a check after its revision lists what is left under *How it was drafted*.
3. **Publish** now, or **Schedule** for a date and time (the API's site worker publishes it then). The
   post's date is the day it first went live (Lagos time).
4. **Rebuild.** Publishing (or unpublishing, archiving, or saving a change to a live post) records a
   rebuild request. Within about 20 seconds of the last change — never more often than once every two
   minutes — the API calls GitHub's `workflow_dispatch` for `deploy-web.yml` on `main`. The *Blog*
   page shows changes waiting, the last rebuild asked for, and the deploy workflow's newest run.
5. **Deploy.** `deploy-web.yml` runs `node tools/blog/build.mjs --api`, which reads every live post from
   `GET https://api.notefusion.studio/api/blog/published` and writes the blog, the feed, the sitemap,
   the home-page strip and the hymn pages' "On the blog" lists, checks the result (warnings only), deploys
   to Vercel and pings IndexNow. A post is live a few minutes after you press Publish.

**A clean Gemini draft publishes itself.** A draft that passes every check — no blockers and no advice
left after its one revision — goes live as soon as it is written, and the site is rebuilt; one with
problems left stays a Draft with its notes. At start-up the API also publishes any Gemini draft written
while drafts were kept, if nobody has touched it and it still passes. `Blog__AutoPublishDrafts=false`
(the `BLOG_AUTOPUBLISH_DRAFTS` variable) keeps every draft for review. Hand-written posts are never
published without you.

If the deploy cannot read the posts from the API (after waiting up to 15 minutes, which covers an API
deploy racing the website's), it **fails**, and Vercel keeps serving the previous deployment: a site
without its blog is never published. Re-run it from Actions, or press *Rebuild now* in the console,
once the API answers. A post the build still cannot render (it should not happen: the API refuses to
publish one) is left out with a warning in the deploy log rather than stopping the whole site.

### The checks

The API checks a post the way the site's build will read it (`src/NoteFusion.Application/Blog/BlogChecks.cs`):

- **Blockers** (publishing is refused): a slug that is not lowercase words joined by hyphens; no title
  or description, or a description over 160 characters; no tags, or tags that are not lowercase-hyphenated;
  an author the site does not know; a question without an answer; a cover without alt text, width and
  height; a `#` heading in the body (the title is the page's only h1); an image without its size; a
  ```` ```solfa ```` block the build could not render (unknown hymn, bars outside the hymn, not a key…);
  raw script/iframe/style/form HTML; a title another live post has; an internal link to a page that
  does not exist.
- **Advice** (the old drafter's quality checks, sentence for sentence): title 20–60 characters,
  description 110–155, 800–2,200 words (the drafter asks for 1,400–1,900), at least four `##` sections, 3–8 FAQ answers of 12+ words
  each ending in a question mark, no FAQ section in the body, the topic's required links and a link to
  `/app`, no external links, no stock AI phrases ("as an AI", "delve"…), no placeholders (TODO,
  lorem…), no percentages, "studies show", attributed quotes or testimonials, and no solfa written by
  hand. A Gemini draft must pass all of them (blockers and advice) or it is revised once; a post you
  write yourself is only warned.

Hymns, pages and authors are checked against **`/blog/catalogue.json`** on the live site, which the
deploy's build writes (the hymns with their opening line exactly as the engine writes it, every page
path, the author ids). If it cannot be read, the hymn and link checks are skipped (the console says so).

### The rules the model is given

The system instruction (`src/NoteFusion.Application/Blog/Drafting/BlogPrompt.cs`, ported word for word
from the old `tools/blog/lib/prompt.mjs`) tells the model to write as Francis, for choirs in the UK, the
US, Europe and worldwide that read movable-doh, la-based-minor Tonic Solfa, and that it must never invent
statistics, studies, quotes, testimonials or anecdotes; must link only to pages on this site; may
describe only the NoteFusion features it is given; and must never mention prices.

**Solfa is never written by the model.** The prompt carries a catalogue of examples written by
NoteFusion's engine (from the site's `/blog/catalogue.json`): the opening line exactly as the engine
writes it of each hymn encoded by hand (`imported: false`) and of any imported hymn the topic must
link to, and the scales. The model can only cite them as ` ```solfa ` blocks, which the build renders
with the engine. (The 248 imported Open Hymnal Project hymns would double the prompt if every first line
were spelled out; every hymn page stays in the list of pages the post may link to.) A run of
hand-written solfa in the prose fails the checks.

### Model, key and cost

| Setting | Where | Default |
|---|---|---|
| `Gemini__ApiKey` (**required** for drafting) | the API's environment; the deploy passes the `GEMINI_API_KEY` repository secret | — |
| `Gemini__Model` | the API's environment; the deploy passes the `GEMINI_MODEL` repository variable | `gemini-3.8-flash` |
| `Gemini__FallbackModels` | the API's environment; the deploy passes the `GEMINI_FALLBACK_MODELS` repository variable | `gemini-flash-latest,gemini-flash-lite-latest` |
| `Gemini__MaxOutputTokens` | the API's environment | `16384` |
| `Blog__AutoDraftEnabled`, `…Days`, `…TimeUtc`, `…Count` | the API's environment (`BLOG_AUTODRAFT_*` variables) | on, `Mon,Thu`, `05:30`, `1` |

`gemini-3.8-flash` is Google's current stable Flash model: cheap and a good writer. For higher
quality set `GEMINI_MODEL` to a Pro model — at the time of writing `gemini-3.1-pro-preview`. Check the
[model list](https://ai.google.dev/gemini-api/docs/models) when you change it.

The call is `generateContent` at `https://generativelanguage.googleapis.com/v1beta/models/<model>`
with the key in the `x-goog-api-key` header, `responseMimeType: application/json` and a
`responseSchema`, temperature 0.7, through the API's `OutboundResilience` (a four-minute limit per
attempt; no retries or circuit breaker of its own — the drafter paces itself, see below). A 429, a 5xx
or a dropped connection is tried up to five times with a growing pause (15, 30, 60, 60 s; a
`Retry-After` the API sends wins): Gemini's "high demand" 503s can last minutes. If the model is still
overloaded or rate-limited after that (or its id is gone, a 404), the draft falls back to
`gemini-flash-latest`, then `gemini-flash-lite-latest`, two tries each (`Gemini__FallbackModels`, a
comma-separated list, changes it; `none` turns it off). A refused key (401/403), a blocked prompt or any
other refusal never falls back: it stops the batch with the API's own message. The revision goes to
the model that wrote the draft, and the draft and its batch record that model. If every model is
unavailable, the batch stops (it would only fail the same way) and says why in the run. Thinking
tokens count against the output limit, which is why it is 16,384 rather than 8,192; a draft cut off by
the limit fails rather than half-writes.

**Cost:** each call's `usageMetadata` (prompt, output, thinking, cached and total tokens) is saved
with the draft and shown in the console (per draft and per batch). Multiply by the rates on Google's
[Gemini API pricing page](https://ai.google.dev/gemini-api/docs/pricing). A draft is one call, or two
when a revision is needed.

### One-time setup

1. **Gemini.** The `GEMINI_API_KEY` repository secret already exists (the old drafter used it); the
   API deploy (`deploy.yml`) now passes it to the API as `Gemini__ApiKey`. Nothing to do unless you
   rotate it.
2. **GitHub token for rebuilds.** Create a fine-grained personal access token: GitHub → Settings →
   Developer settings → Fine-grained tokens → *Generate new token*; Resource owner: the repository's
   owner; Repository access: *Only select repositories* → `Notefusion`; Repository permissions →
   **Actions: Read and write**. Add it as the repository secret **`GH_DEPLOY_TOKEN`** (Settings →
   Secrets and variables → Actions → New repository secret). The API deploy passes it as
   `GitHub__Token`. Without it, publishing works but the site only picks the post up at its next deploy.
3. Redeploy the API (Actions → *Deploy to EC2* → *Run workflow*) after adding or changing either.

## Writing a post by hand

*Blog → New post*. The address (slug) follows the title until you change it, and is fixed once the post
has been published. Markdown, sections from `##`:

Images: `![alt text](/assets/blog/picture.jpg "1200x675")` — the size in the title is required so
the page does not jump as the image loads; images are lazy-loaded. An image on a line of its own is
a figure; `"1200x675 | A caption"` gives it a caption. (Images themselves are files under
`web-site/assets/blog/`, committed like any other asset; a cover can also be any `https://` address.)

A quote block is a **pull quote** (a line from the post set large; never words put in someone
else's mouth). A quote block that starts with `[!TIP]` or `[!NOTE]` is a **callout** box:

```markdown
> [!TIP]
> If you are new to solfa altogether, start with [how to read Tonic Solfa](/blog/how-to-read-tonic-solfa).
```

Solfa examples are ` ```solfa ` blocks, rendered by NoteFusion's engine when the site is built (the
console's preview shows a placeholder for them):

````markdown
```solfa
hymn: amazing-grace     # any published hymn
bars: 1-5               # optional; the pickup bar counts as bar 1
key: F major            # optional; the same bars in another key (the solfa does not change)
words: false            # optional
```

```solfa
scale: A minor          # any major or minor key
harmonic: true          # optional: the raised seventh (se)
```
````

Each post gets: a header with a kicker (its first tag), the title, the dek and the byline (the
author's photo or initials, the date, reading time and the number of reads); an "In this article"
box (from four sections up); share links (WhatsApp, X, Facebook, copy link: plain links, no
third-party script); the author card; related posts by tag ("Keep reading"), the hymns its solfa blocks
cite, the "Transcribe your own song" call to action, canonical URL, Open Graph and Twitter cards (the
default card unless the post has a cover), `BlogPosting`, `BreadcrumbList` and `FAQPage` JSON-LD, and an
entry in the sitemap and the RSS feed (`/blog/feed.xml`). The SEO title and description, when set,
replace `<title>` ("{Title} | NoteFusion") and the meta/Open Graph description. An edit to a live post
on a later day shows as "Updated …" and moves the sitemap's `lastmod`. Tag pages are `noindex` (they
only repeat summaries) and stay out of the sitemap.

## Topics

*Blog → Topics* is the drafting queue (it used to be `content/blog/topics.yml`; the `AddBlog` migration
moved its 40 topics into the database). Each topic is the post's address, the search phrase it answers,
what the searcher wants, the angle, and the site pages it must link to (`/app` is always required; a
link to a page that is not live yet is simply not required until it is). "Generate" takes the first
*Unused* topics from the top whose address has no post; move a topic up to draft it sooner, mark it
*Skipped* to keep it without drafting it, or press the sparkle button to draft one now. Once the blog has impressions,
use Search Console's *Performance* report to reorder the queue.

## Building the site locally

```bash
cd tools/blog && npm ci         # once
node tools/blog/build.mjs       # from the repo root: what is committed (content/ only: hymns, no posts)
node tools/blog/check.mjs       # what CI runs: staleness, links, JSON-LD, sitemap, feed, PDFs
cd tools/blog && npm test       # generator tests (the API path from tests/fixtures/published.json)
node tools/blog/build.mjs --api --site /tmp/site   # a preview with the live posts, into a copy
python3 -m http.server -d /tmp/site 8000            # then http://localhost:8000/blog/
```

**Never edit `web-site/blog/**`, `web-site/hymns/**` or the latest-posts block in
`web-site/index.html` by hand**, and never commit a build made with `--api`: the committed output is
built from `content/` alone (CI's staleness check fails otherwise). The `Blog & hymn pages` workflow
(`.github/workflows/blog-check.yml`) runs the tests and the check on every pull request that touches
`content/`, `tools/blog/` or `web-site/`.

The old way — Markdown files in `content/blog` and a GitHub workflow (`blog-draft.yml`, `draft.mjs`)
opening a pull request per draft — is retired. `content/blog` is still read if a `.md` post is put
there (an API post with the same slug or title wins), but nothing uses it.

## Hymns

Each hymn page shows the doh, the solfa in the web app's hymn layout with the first verse under it,
the same solfa as plain text line by line, the staff (MusicXML drawn by the pinned OSMD, the same
file and SRI hash as `/app`), every verse, a piano player that lights the note being played, facts
read off the melody (starting note, range, the notes it uses), a short history, credits, three
questions with answers, and `MusicComposition` + `BreadcrumbList` + `FAQPage` JSON-LD.

**All solfa comes from the engine.** The hymn files hold pitches and durations; the build runs
`web-site/assets/choir.js` — the web mirror of `src/NoteFusion.Core/Solfa` — on them. Correct a
hymn by correcting its notes, never by typing solfa.

### Printable PDFs

Every hymn and tune page has a free A4 PDF beside it, `/hymns/<slug>/<slug>-tonic-solfa.pdf`
(`/hymns/tunes/<slug>/<slug>-tonic-solfa.pdf`), linked by a *Download the solfa (PDF)* button, a link in
"The solfa line by line", `<link rel="alternate" type="application/pdf">` and the page's
`MusicComposition.associatedMedia`. It prints the title, the doh and time, the solfa line by line with the
words of the first verse under each bar — the same bars and characters the page prints (h.view.lines;
`lib/render-pdf.mjs` lays them out, it never writes a syllable) — the other verses in balanced columns,
the credits and a footer with the page's address and the NoteFusion wordmark. One page for most hymns,
two for a long one; a verse that would need a third page is left to the hymn's page and the PDF says so.
No staff: the staff is drawn by OSMD in the browser, and the solfa is what the searches ask for.

- **Generator:** `pdf-lib` + `@pdf-lib/fontkit` (pinned), with the site's fonts embedded and subset —
  JetBrains Mono for the solfa, Geist for the words, Source Serif 4 for the title — from
  `tools/blog/pdf-assets/fonts` (SIL Open Font Licence, the licences beside them; embedding is allowed).
  About 25–40 KB each. Deterministic: dates come from the hymn's `updated`, so a rebuild changes nothing.
- **Built, never committed.** `build.mjs` writes the PDFs with the pages, locally (`web-site/.gitignore`
  keeps them out of git), in `check.mjs` and in the deploy. A few hundred binary files that all change
  when a font or the layout does would grow the repository with every edit; a PDF is built from the same
  content and code as its page, so it cannot go stale. `check.mjs` builds and checks every one: each hymn
  and tune page names its PDF and the PDF exists; it opens, is titled "… in Tonic Solfa" by NoteFusion,
  has at most two pages and stays under 80 KB; and its first line of solfa is the page's, bar for bar.
- **Not in the sitemap.** Google finds a PDF through the page that links it (every hymn page is in the
  sitemap); listing them would double the sitemap with files whose `lastmod` is their page's.

### Seasons and occasions, writers and composers, first lines

- **`/hymns/occasions/<slug>`** (hub `/hymns/occasions`): Advent, Christmas, Epiphany, Lent, Holy Week,
  Good Friday, Easter, Ascension, Thanksgiving, Holy Communion, Evening, Funeral — every occasion in
  `OCCASIONS` (`lib/collections.mjs`) with at least four hymns; the others (Pentecost, Trinity, Harvest,
  Morning, Baptism, Wedding, New Year) appear on their own once the hymnal has four for them. A hymn is
  filed by its `category` (the Open Hymnal's own) or by its `"occasions"` list (`["Christmas"]`; the
  hand-encoded hymns, which have no category, use it; the build refuses an unknown name). The Open
  Hymnal's `topics` are not used: they name what a hymn mentions, not when it is sung. The occasion
  links on `/hymns` replace the old filter buttons; the filter box still finds a season by name.
- **`/hymns/people/<slug>`** (hub `/hymns/people`): everyone credited with words, a translation, music
  or an arrangement on at least two hymns and tune pages, with the dates the hymn pages print (the most
  common, when two files disagree) and their hymns and tunes. One person credited two ways (same surname,
  first name and years: "Fanny Crosby" / "Fanny Jane Crosby") is one page. No biography: only what the
  hymn files say. Names on hymn and tune pages link to these pages.
- **`/hymns/first-lines`**: every hymn's first line and every refrain's, A–Z (quotation marks and accents
  ignored), with an A–Z bar.
- Hymn pages end with "More Christmas hymns" and "More by John Newton" (at most three lists, five links
  each, the hymns after this one so each page links to different ones).

### Public domain, strictly

The build refuses to publish a hymn unless **everyone named (composer, arranger, author,
translator) died before 1955** — or the source is marked `"traditional": true` — and **both words
and music were first published before 1929**. That keeps every page out of copyright in Nigeria
(life + 70 years), the UK and EU (life + 70) and the United States (published before 1929).
Do not add hymns whose words or tune are still in copyright (for example the English words of
*How Great Thou Art*, *Great Is Thy Faithfulness*, or modern worship songs); note that a modern
arrangement or translation of an old hymn can still be protected.

### Importing from the Open Hymnal Project

Most hymns come from the [Open Hymnal Project](http://openhymnal.org/) (edited by Brian J. Dumont),
which publishes its hymns as ABC scores and states each hymn's copyright in the score; its
[copying page](http://openhymnal.org/copying.html) puts the project's own editing and data in the
public domain. Every imported page credits it with a link to the hymn's page there, and
`/hymns/credits` lists the sources, the licences and every hymn's writers.

```bash
mkdir -p /tmp/ohp && cd /tmp/ohp && curl -O http://openhymnal.org/OpenHymnal2014.06-abc.zip   # or the single /Abc/<name>.abc files
unzip -d abc OpenHymnal2014.06-abc.zip                                                     # the scores are data: never run anything from them
node tools/blog/import/run.mjs --src /tmp/ohp/abc --date 2026-10-16    # --dry-run to see the counts only
node tools/blog/build.mjs && node tools/blog/check.mjs
```

The importer reads only the melody voice (the soprano; the top note of a chord), every `w:` verse
and the `W:` verses after the score, and the score's own metadata (`%OHCOMPOSER`, `%OHAUTHOR`,
`%OHTRANSLATOR` with their dates; the years in its `C:` lines; `%OHCATEGORY` and `%OHTOPICS` as the
index's seasons and topics). It never writes solfa: the build runs the engine on the notes. For each
score:

- **Not imported at all** (nothing copied, listed in `tools/blog/import/ohp-report.json`): a licence
  other than plain public domain (a hymn whose only the harmony is licensed is fine — the harmony is
  not used), or anyone named living or dead in 1955 or later, or first published after 1928.
- **Already on the site** (same title, other title or opening words, and the same tune): ours is kept.
  If ours is a words-only draft, its melody is filled in from the score and our first verse is fitted
  to the score's syllables (`has`/`hath`, `Savior`/`Saviour` allowed); the same words to another
  tune become a page of their own, the tune in the title ("When I Survey the Wondrous Cross (Hamburg)").
- **New**: published only when every gate passes — the melody parses (a metre; no triplets, repeats,
  key or metre changes; bars that add up; notes on the quarter-beat grid), the first verse has one
  syllable or held note per note, a singable range (G3–A5, at most a twelfth), and the public-domain
  rule above from the score's own dates. Otherwise it is a draft whose `reviewNotes` say why
  (`"Held back: …"`); nothing is guessed or looked up elsewhere.

Every imported hymn is `"reviewed": false` with `"confidence": "imported, unchecked: …"`, carries
`source`, `sourceUrl`, `licence`, `credits` and `importedFrom`, and its tune's `reviewNotes` say what
to check. Running the importer again rewrites only the files it wrote (and removes those it no longer
produces); hand-written hymns are never touched except to fill a words-only draft. Line breaks in the
verses come from the metre (`%OHMETRICAL`) when the syllables add up, else from punctuation — check
them when you review a hymn.

### Tune pages: importing tunes from the CCEH

The [Christian Classics Ethereal Hymnary](https://www.ccel.org/cceh/index.htm) (CCEH) is an archive
of about 1,400 hymn tunes — tunes only, no words — each with a page (composer, dates, metre, incipits)
and its four-part score as a Noteworthy Composer file, a MIDI file and a PDF. Its
[copyright page](https://www.ccel.org/cceh/cceh_cpr.htm) says the music is in the public domain and
that every file is "free to use in any manner". CCEH judges public domain by the American rule
(published before 1923), so the importer applies **our** rule as well (above): tunes by anyone who died
in 1955 or later (SINE NOMINE, KINGSFOLD as Vaughan Williams set it, FINLANDIA) are never copied.

A tune without words is a **tune page** of its own: `content/hymns/tunes/<slug>.json` with
`"draft": false` is rendered at `/hymns/tunes/<slug>` (the solfa, the same as plain text, the staff,
the piano, the metre with the hymns on this site in that metre, credits and questions), listed in the
`/hymns` A–Z with a **Hymns / Tunes** filter, on `/hymns/credits`, and in the sitemap. A tune file
without `draft` is a hymn's tune, as before; `lib/content.mjs` checks a published tune page against the
public-domain rule for its music. A hymn can use a CCEH tune by naming its slug in `"tune"`.

```bash
# 1. Crawl (polite: one request at a time, 11 s apart as CCEL's robots.txt asks, a descriptive
#    User-Agent; about 9-13 hours for the whole hymnary; a restart resumes where it stopped).
python3 -I tools/blog/import/cceh-crawl.py /path/to/cceh-cache       # outside the repo
# 2. Import whatever is cached so far (run again as the crawl goes on; --dry-run for the counts only).
node tools/blog/import/cceh-run.mjs --cache /path/to/cceh-cache --date 2026-10-16
node tools/blog/build.mjs && node tools/blog/check.mjs
```

The workflow `.github/workflows/hymns-cceh.yml` does all of this on GitHub's runners. It ran every six hours
until the crawl was complete (all 1,398 tune pages, 18 Oct 2026) and now runs only by hand: it crawls for five hours (`--minutes`; the cache, third-party files, rides in the Actions cache and
is never committed), imports, builds and checks, and when at least 15 more tunes would be published than
on main (or the crawl is complete and anything is new) it pushes one commit, authored as the owner, to
the `hymns/cceh-next` branch. It never pushes main or opens a PR. To publish: take the branch, add dates
for the new undated people its run summary lists (the next run imports what they unlock), open the PR
and merge it. Run it by hand from the Actions tab (`crawl_minutes` 0 imports only).

The crawl keeps each tune's page, one MIDI file (the plain four-part score, not a descant, tenor-lead
or alternative arrangement when the page has one) and the Noteworthy score of the same arrangement.
For each tune the importer (`tools/blog/import/cceh*.mjs`; the files are data, read and parsed, never run):

- **The melody** is one of the MIDI file's lines — each staff's top and bottom line, so the tune is
  found in the tenor of a tenor-lead setting too — the one whose opening matches the page's **do-re-mi
  incipit** (any key; about one note in seven may differ). No line matching the incipit: **rejected**,
  never the alto by default. Notes keep their written lengths (Noteworthy plays them short).
- **The bar lines** come from the **Noteworthy score** (`import/nwc.mjs` reads the bars of its first
  staff); a MIDI file has none. Without a readable score they are read off the rhythm and the tune
  is held back. A bar of another length mid-tune, a change of time signature, triplets or notes off
  the semiquaver grid keep it a draft (or, for the last two, leave it out).
- **Refused** (nothing copied): a © on the page or in the MIDI file, anyone named who died in 1955 or
  later (from the page's dates, or `KNOWN_IN_COPYRIGHT` in `import/cceh.mjs` for composers CCEH
  names without dates), a year of 1929 or later for the tune or an arrangement of it.
- **Pre-1850 rule** (founder's decision, 2026-10-16): someone with no death year whose work CCEH dates before 1850 is taken to have died before 1955 (they would have been over 105). It is recorded as `"activeBy": <year>` on the person, never as a death year, and the page credits them as "(fl. <year>)". A composer CCEH credits without a year of their own, above the book that dates the tune ("attr., William Moore" / "Columbian Harmony, 1825"), takes the book's year; an arranger never does.
- **Draft**: anyone named (composer, arranger, harmoniser) without a death year and with no work dated before 1850. The importer uses
  the page's own dates, else the dates our other pages already give the same person (hand-made hymns,
  the Open Hymnal import, other CCEH pages) — nothing is guessed. `tools/blog/import/cceh-dates.json`
  takes dates checked by hand, each with its source (`{"John Zundel": {"born": 1815, "died": 1882,
  "source": "…"}}`); the report's `undatedPeople` lists who would unlock the most tunes. `"correctName"`
  prints a name CCEH misspells as the sources spell it (William F. Sherman → Sherwin), and `"lived"`
  ("19th century") stands in for the years when the sources disagree on who someone was, or give a birth year
  but no death, with `"died"` the latest year they could have died (MONKLAND's John Bernard Wilkes; founder's
  decision, 2026-10-16; KEDRON's Ann B. Spratt, born 1829, by the pre-1850 rule's 105 years).
- **Already on the site**: the same melody as a tune we hold (compared by its intervals, so the key
  does not matter), or as an earlier CCEH tune: ours is kept and nothing is written.

Every imported tune has `"source": "CCEH"`, `sourceUrl` (its CCEH page), `scoreUrl`, `licence`,
`credits`, the composer with dates, `metre`, `key`, `incipit`, `"reviewed": false`,
`"confidence": "imported, unchecked"` and `reviewNotes` with any reasons it was held back; the counts
and every tune's fate are in `tools/blog/import/cceh-report.json`. Re-running rewrites only files it
wrote (and removes those it no longer produces for a page it has read).

**For the hymn matcher**: a published tune page is a whole melody with no words. `tuneMatcherEntry(t)`
in `lib/render-tunes.mjs` gives it as a `"score"` entry in the matcher's index format (slug
`tune-<slug>`, title, tune, url, source, licence, credit, key, time, pickup, tempo, notes, empty lyrics).

### Words set by metre: Watts' Hymns and Spiritual Songs

Words-only hymn books printed no tunes: a hymn in Common Metre was sung to any Common Metre tune. `tools/blog/import/watts.mjs`
does the same for Isaac Watts' *Hymns and Spiritual Songs* (1707; Watts died in 1748). The source is the book's plain text
(Project Gutenberg eBook #13341, an 1818 London printing), downloaded into a directory of its own; the pages name the book,
not the transcription.

```bash
mkdir -p /tmp/watts && curl -L -o /tmp/watts/watts.txt https://www.gutenberg.org/cache/epub/13341/pg13341.txt
node tools/blog/import/watts.mjs --src /tmp/watts/watts.txt --date 2026-10-26             # drafts; --dry-run for the counts
node tools/blog/import/watts.mjs --src /tmp/watts/watts.txt --date 2026-10-26 --publish   # once a person has read them
# His Psalms of David Imitated (1719), eBook #13166, the same way: pages "watts-1719:Psalm 23:2", watts-psalms-report.json
mkdir -p /tmp/watts-psalms && curl -L -o /tmp/watts-psalms/psalms.txt https://www.gutenberg.org/cache/epub/13166/pg13166.txt
node tools/blog/import/watts.mjs --book psalms --src /tmp/watts-psalms/psalms.txt --date 2026-10-26 --publish
```

Each hymn's metre is read off its lines (Common, Long or Short; four-line verses only), and its first verse is laid under a
tune of that metre that sings one syllable to a note (`TUNES` in watts.mjs, checked against the melodies at every run),
picked by the page's slug so a page keeps its tune. Syllables come from `import/syllables.mjs`: how our own hymns already
split a word, then the TeX English hyphenation patterns (the `hyphen` package), then the metre: a line must come to its
metre's count, a word sung short in the old books ("heaven", "power", "list'ning", "guard-ian") may give a syllable to
one read short ("a-broad"), "the" may run into a word beginning with a vowel ("th'e-ter-nal", as the books print it),
and a line that cannot be fitted honestly refuses the hymn (listed in `watts-report.json`, nothing written). A hymn we
already have (first line, title or other title) is left alone. The pages carry `"setByMetre": true`, which keeps them out
of hymn recognition (a hummed ST ANNE is offered "O God, Our Help", not every text sung to it) and out of the app's pack.

### Words set by metre: books that print the metre and the author

`tools/blog/import/words-books.mjs` does the same for words-only books that print each hymn's metre and author:
`--book 1848`, *A Book of Hymns for Public and Private Devotion* (Samuel Longfellow and Samuel Johnson, Boston 1848; Project
Gutenberg eBook #33180, the fifteenth edition of 1866 with its supplement), `--book 1846`, *Hymns for Christian
Devotion* (John G. Adams and Edwin H. Chapin, Boston 1846; eBook #20476, the twenty-second edition of 1853), and
`--book olney`, the *Olney Hymns* of John Newton and William Cowper (London 1779, the first edition, from the Christian
Classics Ethereal Library's plain text, marked public domain: `parseOlney`, the metre printed as "8,6,8,6", the margin's
scripture and the capitals of the divine names left out, each of its three books from Hymn 1):

```bash
mkdir -p /tmp/hymns-1848 && curl -L -o /tmp/hymns-1848/book.txt https://www.gutenberg.org/cache/epub/33180/pg33180.txt
mkdir -p /tmp/hymns-1846 && curl -L -o /tmp/hymns-1846/book.txt https://www.gutenberg.org/cache/epub/20476/pg20476.txt
node tools/blog/import/words-books.mjs --book 1848 --src /tmp/hymns-1848/book.txt --date 2026-10-26 [--publish] [--dry-run]
node tools/blog/import/words-books.mjs --book 1846 --src /tmp/hymns-1846/book.txt --date 2026-10-26 [--publish] [--dry-run]
mkdir -p /tmp/olney && curl -L -o /tmp/olney/olney.txt https://www.ccel.org/ccel/n/newton/olneyhymns/cache/olneyhymns.txt
node tools/blog/import/words-books.mjs --book olney --src /tmp/olney/olney.txt --date 2026-10-26 [--publish] [--dry-run]
```

The metre is the book's label read with the verse's length ("8 & 7s" or "8s. & 7s." in eight lines is 8.7.8.7 D; "L. M.
6l." is 8.8.8.8.8.8; "P. M." and "(Peculiar.)" give none), set to a tune of that metre from `METRES` in the importer
(Common, Long and Short Metre share Watts' tunes; 7s, 8.7s, 7.6 D, 10s, 11.10s, 6.6.4.6.6.6.4, H.M. and the doubles have
their own). The books name most authors by surname: `AUTHORS` names those we can place, in full with their dates,
matching the people already on our pages ("Tate & Brady" is both; ", alt." marks words the compilers changed); a surname
that could be more than one writer, and a hymn translated by someone the book does not name (Breviary, German, Luther,
Neale…), is left out. "Anonymous" and the collections the books cite stand as `Anonymous`, and the page says which
collection. The books give only the year of their printing, so the pages carry `"textPublishedBy": true`: their
public-domain answer says the words were "in print by" 1848 (1866 for that book's supplement, hymns 480–600), 1853 or 1779,
never a made-up first publication. A header the transcription spaced oddly is still read as a header, so no hymn's verses
run into the one before. Skipped hymns and why are in `hymns-<book>-report.json`.

John Brownlie's five books of translations from the Greek service books and the Latin hymns of the early Church
(`--book early-church` 1896, `greek-church` 1900, `greek-office` 1904, `east` (undated; the 1911 book calls itself the
sixth series after it, so "in print by 1911"), `morningland` 1911; Gutenberg #44039, #27848, #31157, #28479, #29480)
print no metre: `parseNumbered` reads verses numbered I, II on lines of their own, and `inferPattern` takes the metre
most of the lines sing of those we hold tunes for. The words are credited as hymn books credit them, "Traditional
Greek" (or Latin) translated by John Brownlie (1857–1925), and the page quotes whom the book names ("By St. Cosmas, 760
A.D.", "Attributed to Francis Xavier").

The *Evangelical Lutheran Hymn-Book* (abridged edition, Concordia, St. Louis 1927; Gutenberg #76498; `--book lutheran`,
`import/lutheran-1927.mjs`) prints each hymn's metre and, at its end, who wrote it in full or with initials ("H. Bonar,
1846.", "B. Schmolck, 1734; C. Winkworth, tr., 1862."). `NAMES` names them in full with their dates and the language they
wrote in; a hymn from German or Latin is taken only with its translator named, so the translations the book prints
without one (its own committee's, mostly) are left out. The pages say "in print by 1927".

Every book is held to the stresses of its tunes: the 8.7 metres' tunes we hold are trochaic, so words whose 8-syllable
lines mostly end on a stressed syllable ("Alas, my God! my sins are great") are iambs and are left out
(`iambsOnTrochees`), rather than sung with every stress wrong.

A hymn several books print is the first book's page, in `SET_BY_METRE_ORDER` (watts.mjs): Watts' hymns, his psalms,
Olney, the 1848 book, the 1846 book, Brownlie's, then the 1927 Lutheran book. Each importer leaves alone what is hand-set or in a book before it and takes no notice of the
books after it, so the pages do not depend on which ran last; run them in that order.

*The Christian Hymn Book* (Campbell, 1865) prints no authors and the *St. Gregory Hymnal* (1920) gives each hymn its own
tune, so neither is imported this way.

### Adding or correcting a hymn

1. **The tune** — `content/hymns/tunes/<tune>.json`:

   ```json
   {
     "name": "NEW BRITAIN",
     "music": [{ "name": "Edwin O. Excell", "born": 1851, "died": 1921, "role": "Arranged (1900)" }],
     "musicPublished": 1829,
     "key": "G major",
     "time": "3/4",
     "tempo": 76,
     "pickup": 1,
     "lineBars": 4,
     "melody": "D4:1 | G4:2 B4:.5 G4:.5 | B4:2 A4:1 | …",
     "reviewed": false,
     "reviewNotes": "what to check"
   }
   ```

   The melody is `PITCH:BEATS` with `|` between bars: pitches as `G4`, `F#4`, `Bb3` (C4 is middle
   C), beats in crotchets (`1` a crotchet, `.5` a quaver, `1.5` a dotted crotchet, `3` a dotted
   minim), `r:1` a rest, and a trailing `~` ties a note into the next one of the same pitch (a note
   held over a bar line). Every bar must add up; a `pickup` bar holds that many beats and the last
   bar the rest of a bar. Notes fall on the quarter-beat grid: `.25` is a semiquaver and `.75` a
   dotted quaver. A tune on the half-beat grid is laid out by the engine's own `hymnRows`; a tune
   with quarter-beat notes splits a half-beat cell into its two quarters, joined by the tonic solfa
   quarter-beat comma: `d -,r` is a dotted quaver and a semiquaver, `d,r` two semiquavers. On the
   page the octave marks (`s,` `d'`) are drawn small and low or high against their letter, so they
   never read as that comma; copied text is exactly the engine's. `lineBars` is how many bars go on
   a line of the solfa grid (a number, or a list such as `[2, 2, 2, 3]`); two suits 4/4 tunes.

   A quick way to get the notes: sing or play the tune into NoteFusion and copy the pitches from
   the sheet, then check them against the book.

2. **The hymn** — `content/hymns/<slug>.json` (the file name is the URL):

   ```json
   {
     "title": "Amazing Grace",
     "tune": "new-britain",
     "text": [{ "name": "John Newton", "born": 1725, "died": 1807, "role": "Words, Olney Hymns (1779)" }],
     "textPublished": 1779,
     "description": "≤ 160 characters for search results",
     "about": ["A paragraph of history: only facts you are sure of."],
     "underlay": "A-maz-ing_ grace! how sweet the sound, …",
     "verses": [{ "lines": ["Amazing grace! how sweet the sound", "…"] }, { "label": "Refrain", "lines": ["…"] }],
     "updated": "2026-10-15",
     "reviewed": false,
     "draft": false
   }
   ```

   `underlay` is the first verse split into one syllable per note: hyphens join the syllables of a
   word (`A-maz-ing`), and `_` after a syllable carries it over one more note (`ing_` is sung on two
   notes). The build fails if the syllables and notes do not match one for one. Optional:
   `"shortTitle"` (used in the page title), `"note"` on a verse, `"alsoKnownAs"`, `"category"` (the
   source's season or occasion), `"occasions"` (the seasons and occasions it is sung at, from
   `OCCASIONS` in `lib/collections.mjs`, for a hymn without a category) and `"topics"`, and for a hymn taken
   from a collection `"source"`, `"sourceUrl"`, `"licence"` and `"credits"` (shown in its credit
   line). A person may have `"lived": "5th century"` when the source dates them only roughly. A
   draft may wait for its facts; the public-domain rule is enforced when it is published.

3. Rebuild, check, preview, commit: `node tools/blog/build.mjs && node tools/blog/check.mjs`.

## Getting found: Search Console, Bing and IndexNow

Google no longer accepts sitemap "pings"; it reads `robots.txt` (which points at
`https://notefusion.studio/sitemap.xml`) and whatever you submit in Search Console. Do this once:

**Google Search Console**
1. Go to [search.google.com/search-console](https://search.google.com/search-console) → *Add
   property* → **Domain** → `notefusion.studio`.
2. Google shows a TXT record (`google-site-verification=…`). Add it to the domain's DNS — if the
   domain's DNS is on Vercel: Vercel dashboard → *Domains* → `notefusion.studio` → *DNS Records* →
   add a `TXT` record for `@` with that value. Back in Search Console, click *Verify* (DNS can take
   a few minutes to an hour).
3. *Sitemaps* → enter `sitemap.xml` → *Submit*. The status should become "Success" with the
   discovered pages.
4. *URL inspection* → paste `https://notefusion.studio/blog` and `https://notefusion.studio/hymns`
   → *Request indexing*. Do the same for a new post on publishing day if you are in a hurry.
5. Over the following weeks: *Pages* shows what is indexed and why anything is not; *Performance*
   shows the searches people find you with — use it to reorder the topic queue; the
   *Enhancements* reports show whether the structured data (breadcrumbs and the like) is valid.

**Bing Webmaster Tools** (Bing's index is also used by other search services)
1. Go to [bing.com/webmasters](https://www.bing.com/webmasters) and sign in.
2. Choose **Import from Google Search Console** (quickest — it brings the verified site and the
   sitemap), or add `https://notefusion.studio` and verify it with the DNS record it gives you.
3. Check *Sitemaps* lists `https://notefusion.studio/sitemap.xml`.

**IndexNow** is automatic. After each deploy, `deploy-web.yml` runs `tools/blog/indexnow.mjs`, which
lists the blog and hymn pages added, changed or removed — by comparing the live sitemap saved before
the deploy with the one just built (new or gone URLs, a new `lastmod`: this is how posts published from
the console are found, since they are never committed), plus, on a push, the committed pages changed
since the previous commit — and posts them to `api.indexnow.org` with the site's key. Bing, Yandex, Seznam,
Naver and the other IndexNow engines recrawl them within hours (Google does not use IndexNow). The
key is the public file `web-site/<key>.txt`, written by the build from `INDEXNOW_KEY` in
`tools/blog/lib/site.mjs`; Bing Webmaster Tools → *IndexNow* shows the URLs it received. A failed
ping is a warning in the deploy log, never a failed deploy.

## Notes on the implementation

- **Headers and CSP.** The marketing pages' enforced CSP sets only `object-src`, `base-uri` and
  `frame-ancestors`, so the JSON-LD and JSON data blocks (which are data, not executed) and the
  scripts load as on the other public pages. The Report-Only policy now also lists the pinned OSMD
  URL, so drawing the staff on hymn pages does not produce reports.
- **Look.** Headlines and reading text are set in Source Serif 4 (Google Fonts, already allowed by
  the CSP), the interface in Inter; the reading column is about 68 characters wide. Hairline rules
  rather than cards, one accent colour, no gradients or shadows. Every colour is a custom property
  (`site-pages.css` for the shell, `blog.css` for the pages) with a dark value beside the light one.
- **Light, dark and System.** Every public page (home, policies, blog, hymns) loads
  `assets/theme-boot.js` as a blocking `<script src>` in `<head>` with `data-default="system"`, so
  the page is drawn in the right theme from the first paint and follows the device until the reader
  chooses. The header's toggle (`assets/site-theme.js`) cycles Light → Dark → System and saves the
  choice under `nf.web.theme`, the same key the web app's own switch uses, so it carries between
  the site and `/app` (where no choice still means Light). No inline script is involved. The staff
  on hymn pages is engraved on a light "paper" card in both themes; AdSense slots that come back
  empty are hidden, and in dark mode a filled one sits in a light frame of its own.
- **Phones.** The solfa grid and the line-by-line text wrap at bar lines on a narrow screen: a bar
  (its notes with their words under them) is never split and never scrolls out of its box. The
  staff is drawn smaller on a narrow box (OSMD zoom 0.5–0.85 below 760px, so a phone gets two to
  three bars a line) and is redrawn when the window is resized or the phone turned.
- **Number of reads.** `assets/blog.js` fills every `[data-reads-path]` (the byline, the front page,
  "Keep reading") from the API's `GET /api/blog/reads?paths=/blog/a,/blog/b` in one request. A read
  is one browser (the tracker's visitor id) that viewed the page, counted from the first-party page
  views `track.js` records, leaving out every browser that was ever signed in as an admin or
  internal account; web events are kept 180 days, so it is readers over that window. Fewer than
  five shows "New"; "0 reads" is never shown; if the API cannot be reached the count stays hidden
  (its room is kept, so nothing moves). The API caches each page's count for five minutes and
  limits each address to 120 requests a minute. The count is never written into the HTML, so it
  never makes the committed pages stale.
- **Speed.** Pages are static HTML; the solfa is text; the only scripts are the theme boot, the
  header toggle, `blog.js` on blog pages, the first-party tracker, AdSense (as on the other public pages),
  and on hymn pages `choir.js` + `hymn.js` (deferred), which load OSMD only when the staff scrolls
  into view and create the audio context only when Play is pressed. Images need a width and height.
  To keep ads off the blog and hymn pages, set `ADSENSE_CLIENT` to `null` in
  `tools/blog/lib/site.mjs` and rebuild.
- **Analytics.** Every generated page loads `assets/track.js`, so blog and hymn traffic appears in
  the admin dashboard's *Website traffic*; the call-to-action buttons are named for click tracking
  ("CTA: blog", "CTA: hymn"), and playing a hymn records the action "Hymn played".
- **Updating the shared assets.** `vercel.json` makes browsers revalidate `/assets/*.css` and
  `*.js` on every load, but follow the site's convention anyway: bump the `?v=` numbers in
  `ASSET_VERSION` (`tools/blog/lib/site.mjs`) and rebuild when you change `blog.css`, `blog.js`,
  `site-pages.css`, `site-theme.js`, `theme-boot.js` or `hymn.js` (the hand-written pages carry the
  same numbers by hand).
- **Author photo.** `content/authors/<id>.md` takes an optional `photo: /assets/authors/<id>.jpg`
  (square, at least 192×192). It is shown in the byline, the author card and the author page, and
  added to the `BlogPosting` and `ProfilePage` JSON-LD; without one the pages show the author's
  initials.
